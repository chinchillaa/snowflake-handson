# 解説：Time Travel と Zero-Copy Clone（演習5の背景）

## Time Travel とは

Time Travel は、過去の時点のテーブルの状態を参照・復旧できる機能です。

```sql
-- 時刻を指定して過去を見る
SELECT * FROM orders AT (TIMESTAMP => $before_update_ts);

-- 「変更の直前」を見る書き方もある
SELECT * FROM orders BEFORE (STATEMENT => '<クエリID>');
```

使える場面：

- 間違った UPDATE / DELETE の復旧
- 「先週末時点の数字でレポートを作り直す」ような、時点を指定した再現
- 変更前後の比較（監査や検証）

仕組みの要点：Snowflake はデータの変更を履歴として保持しており、その保持期間（リテンション期間）内であれば過去を参照できます。保持期間はエディションやテーブル設定により異なり、期間を過ぎたデータは参照できません。「無期限に残るバックアップ」とは別物として理解してください。

また、間違えてテーブル自体を消してしまった場合は `UNDROP TABLE` で戻せる場合があります（チャレンジ課題で体験します）。

## Zero-Copy Clone とは

`CLONE` は、テーブル（やスキーマ、データベース）のコピーを作る機能です。「Zero-Copy」の名前の通り、**作った瞬間はデータの実体を複製しません**。元データへの参照を持つだけなので、大きなテーブルでも一瞬で作れ、ストレージもほぼ増えません。

- コピー側でデータを変更すると、その変更した部分だけが新しいデータとして保存されます（差分課金）
- 元側を変更しても、コピー側には影響しません（逆も同じ）

通常の `CREATE TABLE ... AS SELECT ...`（実データを全てコピーする）との違い：

| | CLONE | CREATE TABLE AS SELECT |
|---|---|---|
| 作成にかかる時間 | 一瞬 | データ量に比例 |
| 作成直後のストレージ | ほぼ増えない | 元と同じ量が増える |
| 主な用途 | 検証環境の複製、本番データでの開発・テスト | 集計結果の保存など |

## 考えてみよう

本番テーブルのコピーで新機能をテストしたいとき、CLONE と CREATE TABLE AS SELECT のどちらを選ぶべきでしょう。判断の軸は「コピーの速さとストレージ」だけではありません。「コピー元が本番データであること自体のリスク（個人情報など）」も実務では論点になります。
